# dsh-plan-store

Database-backed plan store for [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness):
plans live in SQLite instead of hand-written markdown files, the agent manages them through
`plan_*` tools, and the web GUI renders them as a kanban board next to a session goal/todo tab.

Design goals, in order: **comfortable task planning**, **low token cost**, and keeping the
workspace plan file required by the user's global rules in sync with the database.

## Requirements

- Node.js `^22.19.0 || >=24.0.0` (`node:sqlite` with FTS5; a `LIKE` fallback is used when FTS5 is
  unavailable).
- A dsh profile with `@deepseek-ai/dsh-tools`, `dsh-system-prompt`, `dsh-host-webserver`,
  `dsh-settings` (all `0.1.5-rc.3` in the tested setup).

## Install

```sh
dsh plugin --profile web add /path/to/dsh-plan-store
dsh --profile web --dump-config   # the plugin line must be present
# restart the profile afterwards: the server half is loaded from lib/index.js
```

The package ships a bundle patch (`cordis.patch.yml`) and a browser client (`lib/client.js`), so the
reconciler adds it to `dsh.profile.bundles` on its own.

## Storage

| What | Where |
| --- | --- |
| Database | `$DSH_HOME/plan-store/plans.db` (default `~/.dsh/plan-store/plans.db`), WAL |
| Exported plan | `<workspace>/.dsh/plans/<slug>.md`, markdown with checkboxes |

The database is the source of truth. The markdown file is generated by `plan_export` (the global
rules require that file); it is never edited by hand and never needs to be read back.

Model: **plan → phases → tasks**, plus an append-only journal.

- plan status: `backlog`, `active`, `blocked`, `done`, `archived`
- phase/task status: `todo`, `doing`, `blocked`, `done`
- plan priority: `low`, `normal`, `high`, `urgent`
- journal kinds: `created`, `updated`, `status`, `phase`, `task`, `export`, `archived`, `purged`

Status automation keeps the board honest: the first task in `doing` activates the plan, finishing
every task completes it, reopening a task reopens it, and phases follow their own tasks the same
way. Manual `blocked`/`archived` states are never overwritten.

## Tools

| Tool | What it does |
| --- | --- |
| `plan_create` | Create a plan with phases and tasks. Returns the full tree |
| `plan_list` | List plans with progress and the next open task (default 20) |
| `plan_get` | Read one plan as a full tree with its journal |
| `plan_search` | Full-text search over plans and tasks (FTS5, default 10 hits) |
| `plan_update` | Update title, description, status, priority, tags or workspace |
| `plan_delete` | Archive a plan (soft delete) |
| `plan_purge` | Delete a plan for good (requires `confirm: true`) |
| `plan_phase_add` / `plan_phase_update` / `plan_phase_delete` | Manage phases |
| `plan_task_add` / `plan_task_update` / `plan_task_delete` | Manage tasks, including done/not done |
| `plan_export` | Write `.dsh/plans/<slug>.md` |
| `plan_status` | Counters, stale plans, database location |
| `plan_import_session` | Import the session goal and todos into a plan (idempotent) |

All tools run autonomously; only `plan_purge` requires an explicit confirmation argument.

Every plan mutation also mirrors the touched plan into the session **todo panel**: the plugin appends
`todo/write` with that plan's tasks (each marked `[plan:<id>] …`) merged over the current list, so items
the model wrote by hand survive. `blocked` tasks show as pending, at most one item is `in_progress`
unless `todoParallelInProgress` is on, and the mirror is capped by `todoMaxItems`. A finished plan
(`done` or `archived`) mirrors nothing, so its items leave the panel once every task is done and come
back if a task is reopened. The host resets its todo list on `turn/start`, so the panel is refilled by
the next `plan_*` call.

The same mutations keep the session **goal** aligned with the plan: a live plan sets the objective
`Complete the plan: <title>`, created and immediately disarmed so the goal is visible in the chat
without starting the automatic continuation rounds of the goal driver. A finished or archived plan
clears that goal, and a goal owned by the user or another plugin (a different objective prefix) is left
untouched. Disable with `syncGoal`.

## Human command

```
/plans            # list plans
/plans status     # store counters and paths
/plans export     # export every plan of the session workspace
/plans export p_x # export one plan
```

## Web GUI

- **Plan Board** — swimlanes (rows = plans, sub-rows = phases, columns = task statuses) with HTML5
  drag&drop, per-plan progress, filters (workspace, status, text, archived), task and plan drawers
  with the journal, and create/edit/export/archive actions. Inactive plans (`backlog`, `done`,
  `archived`) start collapsed as a single header row with a `▸`/`▾` toggle; `active` and `blocked`
  lanes start expanded, and manual toggles last until the page reloads.
- **Goals & Todos** — the current session's goal (resume/pause/complete/block/edit) and todo list
  (status cycling, add, remove) with an **Import into plan** button.
- **Settings → Plan Board** — the settings card for the namespace below.

Both views are reached from the view tabs next to the conversation; the plugin deliberately adds no
sidebar buttons.

Goal and todo live in the session log, so they are read through the session projections and written
back through `ctx.goals` (compare-and-set) and `Session.append('todo/write', …)`. Only sessions that
are live in the running dsh process can be shown or changed.

## HTTP API

Loopback only, under the configured `webPath` (default `/plan-store`):

```
GET  /api/plans?workspace=&status=&query=&includeArchived=&limit=
GET  /api/plan?id=&eventLimit=
GET  /api/search?q=&workspace=&limit=
GET  /api/workspaces
GET  /api/status?workspace=
GET  /api/config
GET  /api/session/state?sessionId=
POST /api/plan/create|update|delete|purge
POST /api/phase/add|update|delete
POST /api/task/add|update|delete|move
POST /api/export
POST /api/session/goal|todos|import
```

## Settings

| Option | Default | Meaning |
| --- | --- | --- |
| `storageRoot` | `''` → `$DSH_HOME/plan-store` | Database directory (a change needs a plugin restart) |
| `webPath` | `/plan-store` | Base path of the API and the board |
| `exportDir` | `.dsh/plans` | Export directory relative to the workspace root |
| `autoExport` | `true` | Remind the agent to export a plan after changes |
| `promptActivePlans` | `true` | Include the active-plan summary in the system prompt |
| `promptActiveLimit` | `5` | Maximum number of plans in that summary (0 disables it) |
| `stalePlanDays` | `14` | Age after which a plan is reported as stale |
| `syncTodos` | `true` | Mirror the touched plan into the session todo panel after every change |
| `syncGoal` | `true` | Mirror the touched plan into the session goal (created disarmed) |
| `todoParallelInProgress` | `false` | Allow several in-progress items in the mirrored list |
| `todoMaxItems` | `25` | Maximum number of items mirrored from one plan |
| `systemPrompt` | built-in English | Guidance injected into the system prompt |

## Token cost

The model sees only a tool's `name`, `description` and `parameters`; output schemas are free.
Measured on 23.09.2026:

| What | Before | After |
| --- | --- | --- |
| Catalog of the tools | ~2539 tokens per request | **~2040** |
| Tool descriptions | ~897 tokens | **~256** |
| `plan_task_update` render on a 12-task plan | ~1040 tokens | **~24** |

How: one-line tool descriptions with shared rules stated once in the prompt section; full trees only
from `plan_create`/`plan_get` while mutations render a headline plus the changed item; bounded
default limits; a bounded, disableable prompt summary; FTS5 snippets instead of bodies.

## Limitations

- Goal and todo are session state, not a store: only live sessions can be shown or modified.
- Existing `.dsh/plans/*.md` files are not imported (by decision); the plugin starts from scratch.
- Todo items have no identity, so the import matches tasks by title.
- The todo mirror needs an agent session (a call without an owning agent is skipped) and the host
  resets the list on `turn/start`; the panel is refilled by the next `plan_*` call.
- Without FTS5 in the Node build, search degrades to a `LIKE` substring match.
